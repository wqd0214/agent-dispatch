1. 现在为什么难用

回看现在的网页和这两天的实际使用，问题不在功能少，而在组织方式：

现象根因
要处理的事找不到页面按「作业列表」组织。待你决定、待审查、失败这些需要你动手的，混在几十行已验收的作业里，只能靠肉眼扫。
一进详情就丢了上下文详情是整页跳转。看完一个再看下一个要来回跳，筛选状态也会丢。
详情页重点不突出头部 10 行元数据占满首屏，真正要看的结论、闸门、产物藏在第三个标签页里。
操作含义不清一个输入框同时当「续派内容 / 驳回原因 / 验收备注」，按钮背后用哪段文字要靠猜。
配置散在三处项目、工程、角色和岗位说明书（派工单模板）只能改文件；模型池在网页；派工工具开关在网页和命令行。改一个角色要记住三个地方。
继承关系看不见全局角色、项目覆盖、模型池继承都是隐式的。「这个角色到底用哪个模型、哪份说明书」得自己推。
长页面滚不到头「模型与角色」一页塞了工具、全部角色的模型池和几十个模型，靠滚动找东西。
不主动告诉你只能自己刷新看，没有角标和通知。

2. 你用客户端做什么

你的日常是：在终端里开主管会话，主管派工给执行者；你在旁边盯盘、做主管做不了的决定、偶尔亲自派工、调配置。按频率排：

① 盯盘现在有什么在跑？哪些卡住了？哪些在等我？——每天很多次
② 做决定回答「待你决定」；对主管拿不准的作业验收或驳回——每天若干次
③ 看过程某个作业实际做了什么、为什么失败；必要时接进执行者界面——按需
④ 派工绕过主管直接派一个作业——偶尔
⑤ 调配置角色、模型池、派工工具、MCP、技能——偶尔，但要改得放心
⑥ 复盘哪个模型、哪个角色效果好；用例判定汇总——每周

所以首页应该服务 ①②，而不是一张作业总表。

3. 设计原则

  1. 以「待我处理」为中心。首页是收件箱：需要你动手的排在最前，处理完就离开视线。
  2. 项目是一级上下文。左上角切换项目，所有视图都在这个项目里；「全部项目」做汇总。
  3. 列表和详情并排。三栏布局（导航 / 列表 / 详情），点哪条看哪条，不跳页、不丢筛选。
  4. 一个操作一个表单。续派、验收、驳回各自独立，按钮写明后果，危险操作二次确认。
  5. 继承关系看得见。每项配置旁边标明「继承自全局」或「本项目覆盖」，一键恢复继承。
  6. 架构不变。命令行和文件仍是唯一真相，客户端只是界面；关掉客户端不影响任何作业。

9. MCP 与技能管理

9.1 思路：登记 + 生效范围

和模型池同一个思路：先在一个地方登记，再决定在哪里启用。

登记表（全局）→全局默认启用哪些→项目里增减→角色里增减→派工时下发给执行者
MCP技能
登记什么名称、类型（本地命令 / 远程地址）、命令与参数、环境变量、说明名称、所在目录、说明（读 SKILL.md 的描述）
从哪导入~/.pi/agent/mcp.json、OpenCode 配置、各工程的 .pi/mcp.json / opencode.json~/.cc-switch/skills、~/.claude/skills、~/.pi/agent/skills、各工程的 .agents/skills
敏感信息数据库密码等只存本机文件，界面上遮罩显示无

9.3 怎么下发给执行者（关键）

原则：派工时按本次作业的配置注入，不改工程里的文件。同一个工程里，测试工程师有浏览器，后端开发工程师没有，互不影响。

执行者技能MCP
OpenCode✅ 配置内容里的 skills.paths✅ 配置内容里的 mcp：加入本次要的，并把工程自带但本次不要的设为禁用。已验证通过环境变量传入配置内容在独立服务模式下生效
pi✅ 命令行 --skill <目录>（可多个），可配 --no-skills 关掉自动发现，做到严格控制⚠ 没有找到命令行入口：pi 只读全局 ~/.pi/agent/mcp.json 和工程的 .pi/mcp.json。需要先验证可行方案（见第 12 节问题 2）
现在测试工程的 MCP 是你手工配在工程目录里的（.pi/mcp.json 等），并且运转良好。迁移时第一步只做「导入 + 展示」，确认客户端看到的和实际一致之后，再逐个角色切换到「由 agent-dispatch 下发」，不会一次性替换掉你现有的配置。

10. 桌面能力

系统通知待你决定、作业失败、作业待审查时通知；点通知直接打开那个作业。可按项目、按类型关闭。
菜单栏 / 托盘图标上显示「待你决定」数量；下拉列出最近要处理的事。
接入执行者界面tmux 方式的作业，一键打开终端并接入（macOS 用「终端」或 iTerm，Linux 用默认终端）。
快捷键⌘N 派工、⌘K 搜索作业、⌘1~4 切换工作台/作业/批次/统计。
自动拉起服务打开客户端时发现服务没在跑就自动启动；关掉窗口不影响作业。
亮色 / 暗色跟随系统，也可固定。

11. 分期计划

期内容说明
一期客户端外壳正在做（Tauri 作业进行中）：窗口、自动拉起服务、系统通知、菜单。不依赖界面改版，改版后直接复用。
二期界面改版：工作台、作业分栏详情、派工面板解决「找不到要处理的事」「操作含义不清」。需要先定第 12 节问题 1。
三期配置中心：项目、工程、角色在线编辑含岗位说明书编辑与预览、继承关系显示、主管规则编辑；把现在只能改文件的配置搬进客户端。
四期MCP 与技能管理登记与导入 → 范围矩阵 → 派工时下发。先做 OpenCode 和 pi 的技能；pi 的 MCP 等第 12 节问题 2 有结论再做。
五期批次视图、统计复盘跨工程的事一眼看进度；模型和角色的效果对比。

每期仍按现在的方式做：我当主管拆作业派给执行者，逐个审查验收，过程在客户端里可见。

12. 需要你定的事

2026-10-04 已定：界面用 Vue 3 + Vite；pi 的 MCP 先验证不改工程文件的办法，不行再由工具管理工程里的配置并在改动前提示确认； 主管会话暂不纳入；敏感信息先存本机文件；只在本机使用。下面保留原问题作为记录。
  1. 界面用什么写。改版后的界面规模远超现在单个 HTML 文件能承载的。建议换成 Vue 3 + Vite（你们前端团队熟悉），构建出的静态文件随工具发布，运行时仍不需要 Node；网页服务和 Tauri 客户端都直接用它。替代方案是继续在单文件里手写，开发会越来越慢。
  2. pi 的 MCP 怎么下发。候选：(a) 先验证 pi 能否通过扩展或环境变量指定额外的 MCP 配置（不改工程文件，最理想）；(b) 不行的话，由 agent-dispatch 管理工程里的 .pi/mcp.json（文件里标明「由 agent-dispatch 生成」，改动前提示你确认）；(c) pi 的 MCP 暂不纳入管理，只管技能。
  3. 主管会话要不要进客户端。现在主管是你在终端里开的会话，工具并不知道它们存在。如果希望在客户端里看到「哪些主管在跑、在管哪些作业」，需要主管启动时登记自己。可以放到后面再说。
  4. 敏感信息。MCP 配置里的数据库密码，是否要放进系统钥匙串（macOS 钥匙串 / Windows 凭据管理器），还是存本机文件即可。
  5. 只在本机用，还是将来要多人或远程访问。这决定了要不要做登录和鉴权；本设计按只在本机用来做。
