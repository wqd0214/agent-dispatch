## 用户补充与改造原则

用户确认 Claude 已能通过后台脚本等待派工单结束并继续原会话。现有 SKILL.md 第 39 行也要求：宿主支持后台命令完成通知时，以该机制执行现有 `agent-dispatch wait`。因此不能将现状表述为缺少等待机制，也不能在未验证前认定必须新增独立调度服务。

适配顺序调整为：先验证 Codex 宿主原生后台命令完成通知是否能复用；能够复用时，只补 Codex 技能、必要的脚本和身份识别；不满足原会话自动继续要求时，才补轻量回传监听与适配器。后文 P1—P4 是条件性实现范围，不默认全部建设。Claude 现有入口与工作方式保持兼容。

## 目标与使用方式

用户打开一个交互式 Codex 主管会话，并始终在这个会话中交流。主管通过现有 agent-dispatch 派 pi 执行，pi 可以使用 headless 或 tmux。后台本地进程等待作业事件，等待期间不调用模型；事件发生后送回原主管会话，由它复核、裁决或续派。

主管结束一轮回复后，交互会话继续打开。用户可在等待期间继续对话。禁止用另一个 `codex exec resume` 并发接管正在使用的主管会话；第一版不做后台 Codex 主管，不新增 Codex 执行者 backend，不依赖 Zed。

主管入口尚待用户确认：Terminal.app 中的 Codex CLI、Codex 桌面应用，或两者。不能将 CLI 的回传验证结果当成桌面应用的验证结果。

## 架构

```text
用户 <-> 当前交互式 Codex 主管
               | start / reply / gate / accept / escalate
               v
         agent-dispatch 作业台账
               |                ^
               v                |
         pi：headless / tmux ----+
               |
        执行回合落定事件
               v
      持久化事件箱 + 本地监听器
               |
      Codex 会话回传适配器
               |
      向准确主管 thread 排入简短通知
```

后台只有监听与投递程序。它不承担模型推理。执行者工作、主管处理事件及用户主动对话仍正常消耗 Token；不宣称总任务零 Token。

## 实施顺序与交付物

### P0：证明原会话可接收事件

使用独立的临时验证会话和目录，不向用户已有工作会话试发消息。

1. 对照用户已可用的 Claude 流程，先用现有 wait 验证 Codex 原生后台命令完成通知：是否能让原会话继续处理，是否需要模型反复轮询，用户能否同时对话。支持后台终端展示不等于支持完成事件自动继续推理。
2. 原生机制不足时，确认用户实际入口和会话 UUID 的可靠取得方式，再验证 `codex queue`；CLI 与目标服务端必须匹配。若目标入口不连同一服务，另行验证其公开连接方式。禁止以当前进程 PPID 或终端标签名代替会话 UUID。
3. 验证空闲时通知是否自动触发处理；忙时是否排队且不打断用户输入；会话关闭、服务断开、错误 UUID 的结果。
4. 验证等待时不产生主管推理调用，不通过循环模型查询完成等待。
5. 输出验证记录：版本、入口、命令、事件时间线、原 thread ID、是否新建会话、调用/用量证据和结论。

放行条件：原交互会话保持可用，无需用户输入“继续”即可处理完成事件。只有消息写入成功但未触发处理，不算通过。

若不通过，先记录明确限制与可行替代，再调整传输层；不能静默退回后台主管或模拟键盘输入。

### P1：主管与作业显式绑定

增加独立的主管绑定记录，区分 agent-dispatch 的稳定主管标识与 Codex thread UUID。复用 dispatcher 关联，不依赖 shell 环境自动继承来保证绑定正确。

记录范围：主管标识、Codex thread UUID、入口/端点、工作目录、事项/批次范围、启用状态、创建时间和版本。允许显式解绑，多个主管不得串单。

交付：绑定、查询、解绑接口，以及机器可读的本主管任务快照。使用新子命名空间，不改变现有 sessions 汇总语义。

### P2：持久化事件箱与监听器

优先从落定后的作业状态生成事件，以 `(主管, 作业, 回合, 事件类型)` 为稳定去重标识。先持久化作业结果，再登记事件；启动时扫描补齐写结果后崩溃造成的缺失事件。

第一版自动通知执行回合结束及运行失败；需要用户决策、人工持有/释放按已有显式状态处理。CLI 内部等待权限如果没有结构化信号，明确标为暂不可检测，不能通过猜测终端文字宣称已支持。

监听器使用本地检查或事件等待，不调用模型；具有单实例锁、状态查询、停止及重启补偿。停止监听不终止执行者。

### P3：向原会话投递与确认

实现独立传输适配器，优先使用通过 P0 验证的 queue 通道。通知包含事件 ID、作业名、回合、当前状态及结果/证据路径，不回传全部日志。

分别记录待投递、投递中、已入队、主管已确认、投递失败。命令返回成功仅表示传输接受，不等于主管已处理或作业已验收。

同一主管合并相近事件，按顺序投递。投递前重新检查绑定、作业回合、人工持有与事项状态；暂停自动回传时保留待处理事件。

重试有限次数并退避，不产生模型轮询。遇到“可能已送达但未记录”的崩溃窗口，采用可追踪的重复事件与确认去重，不能声称端到端严格只投递一次。

### P4：主管技能与用户控制

调整主管流程：派工完成并登记监听后回复用户，当前轮次结束，不再反复调用 wait。事件到达后先确认事件与最新状态，再按现有流程 gate、读取证据、accept/reply/reject/escalate。

人工接手的作业不自动裁决；用户取消或暂停事项后不自动续派。收到重复/过时事件只更新确认记录，不重复执行裁决或创建作业。

提供暂停/继续回传、查看待处理事件、补投及解除绑定的操作。用户在原会话继续提问时，不把用户新消息当成放弃原事项。

更新项目主管说明和随工程发布的技能；全局已安装技能的同步另作显式步骤，不在开发时直接覆盖。

### P5：回归与真实闭环验收

先运行隔离单元/集成测试，再做真实 Codex 主管 + pi 执行者验证。模拟回传成功不能替代真实会话验证。

| 场景 | 必须看到的结果 |
|---|---|
| pi headless 完成 | 原 Codex 会话自动收到结果并复核 |
| pi tmux 完成 | 同样回传；展示/会话存活与作业结论分开 |
| 两个执行者先后或同时结束 | 结果不丢失，不发生并发裁决或重复派工 |
| 主管等待时用户继续对话 | 保持同一 thread，事件按验证过的方式协调 |
| 主管收到结果后 reply | 后续回合结束再次通知，旧回合不重新消费 |
| 监听器重启 | 待投递事件恢复；已确认事件不重复处理 |
| 服务断连、错误/关闭会话 | 明确显示投递失败，保留事件，不创建替代主管 |
| 人工持有、取消、暂停 | 不抢占、不自动续派；重新启用前检查当前状态 |
| 作业结束与登记监听竞态 | 扫描现有结果补齐通知 |
| 空闲等待 | 主管推理请求数不增长，通知前无周期性模型调用 |

必要回归命令：`python3 -m unittest discover -s tests`。新增测试围绕竞态、去重、恢复和状态边界；测试使用临时 AGENT_DISPATCH_HOME，不改真实台账。真实验证只使用独立的小型本地任务，不接生产环境、不做部署或数据变更。

## 实施组织与完成定义

先执行 P0，依据结果选择「原生后台通知 + 最小技能/脚本适配」或「P1/P2 → P3 → P4 回传适配」，最后执行 P5。遵守本工程主管/执行者分工，实际实现通过 agent-dispatch 派工程角色，主管复核证据；每阶段有明确产物，未通过前置验证不扩大实现。

完成必须同时满足：用户一直使用原 Codex 交互会话；pi 两种模式都能回传；等待期间不调用主管模型；原会话自动继续复核；中断、重复及人工接手行为可解释；既有回归通过。当前仅完成现状调查和计划，未实现、未跑真实闭环，也未声明验收通过。
